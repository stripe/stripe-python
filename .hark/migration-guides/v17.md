# Migration guide for v17

## API keys are no longer preserved in pickled StripeObjects

This change affects integrations that persist StripeObjects or webhook events in pickle-backed caches or queues and then make requests through the restored objects. Data-only consumers do not need to rebind credentials.

New pickles omit SDK-held API keys from both the root and nested StripeObjects. Before making object-based requests, supply credentials from the receiving application's secure configuration:

```python
# Before: relied on the producer's key surviving serialization.
customer = pickle.loads(trusted_cached_bytes)
customer.refresh()

# After: use credentials from the worker's secure configuration.
customer = pickle.loads(trusted_cached_bytes)
customer.set_api_key(worker_api_key)
customer.refresh()
```

`set_api_key(api_key: str) -> None` requires a non-empty string and always updates the receiver and every nested StripeObject reachable through payload lists and dictionaries **in place**, including shared objects and cycles. It preserves each object's current connected-account routing, API version, other requestor options, and HTTP-client configuration without changing `stripe.api_key`. No StripeClient or requestor argument is required. Re-pickling the rebound objects still omits SDK-held keys.

The supplied key must be authorized for all retained account contexts. The helper intentionally overwrites differing keys throughout the graph; do not use it on a single mixed-credential graph that needs to retain separate credentials. It does not validate permissions or make an API request.

### Global fallback and explicit rebinding

Plain `pickle.loads()` retains the existing fallback to the receiving process's global API-key configuration. If that is the intended credential, configuring it before loading is an alternative to the setter:

```python
stripe.api_key = worker_api_key
customer = pickle.loads(trusted_cached_bytes)
customer.refresh()
```

A restored object therefore does not necessarily have `api_key is None`. When the global key is absent or inappropriate, use `set_api_key(worker_api_key)` after loading to explicitly replace the key throughout the graph without modifying global configuration. Select the appropriate credentials for the retained account routing.

The setter preserves the requestor configuration currently on each restored object. Pickling does not preserve the producer's custom HTTP client or other private requestor state, and the setter does not recover that configuration.

### Rolling upgrades and stored data

Upgrade consumers to a release with `set_api_key()` and configure their credentials before updated producers send objects without embedded keys. Do not assume pickle compatibility across SDK versions without verifying your application's producer and consumer versions.

Historical pickles can still contain producer API keys. Upgrading or calling `set_api_key()` does not remove credentials from existing cache or queue entries, replicas, or backups. Identify affected entries and invalidate or recreate them using trusted application sources, handling retained copies according to your operational policy. If credentials reached unauthorized readers, follow your incident-response and credential-rotation procedures. Avoid indiscriminate deletion of production queues.

When object behavior is unnecessary, persist only the required data or identifiers instead. Use recursive data conversion appropriate to your installed SDK version rather than assuming older versions' conversion methods remove every nested StripeObject. This change omits SDK-held authentication context, not secrets explicitly placed in payload fields.

Never deserialize untrusted pickle input: loading it can execute arbitrary code. `set_api_key()` does not make deserialization safe.
