# Migration guide for v17
## API keys are no longer preserved in pickled StripeObjects
This change affects integrations that persist StripeObjects caches or queues and then make requests through the restored objects.

New pickles omit API keys from both StripeObjects. Before making object-based requests, supply credentials from the secure configuration:
```python
# Before
customer = pickle.loads(trusted_cached_bytes)
customer.refresh()
# After
customer = pickle.loads(trusted_cached_bytes)
customer.set_api_key(api_key)
customer.refresh()
```
`set_api_key(api_key: str) -> None` requires a non-empty string and  updates the receiver and every nested StripeObject in place. It preserves each object's current connected-account routing, API version, other requestor options, and HTTP-client configuration without changing `stripe.api_key`. Re-pickling the objects still omits SDK-held keys.

The helper intentionally overwrites differing keys throughout the graph.

### Global fallback and explicit rebinding
Plain `pickle.loads()` retains the existing fallback to global API-key configuration. If that is the intended credential, configuring it before loading is an alternative to the setter:
```python
stripe.api_key = api_key
customer = pickle.loads(trusted_cached_bytes)
customer.refresh()
```

A restored object therefore does not necessarily have `api_key is None`. When the global key is absent or inappropriate, use `set_api_key(api_key)` after loading to explicitly replace the key throughout the graph without modifying global configuration.

The setter preserves the requestor configuration currently on each restored object. Pickling does not preserve the producer's custom HTTP client or other private requestor state, and the setter does not recover that configuration.
