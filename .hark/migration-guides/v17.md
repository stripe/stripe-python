# Migration guide for v17
## API keys are no longer preserved in pickled StripeObjects
This affects integrations that persist StripeObjects in caches or queues and then make requests through the restored objects.

New pickles replace API keys with a placeholder, including on nested objects. Unpickled objects retain their data, connected-account routing, and API version, but have no API credentials. Before making object-based requests, call `reattach_api_key()` with a key from secure configuration:

```python
# Before
customer = pickle.loads(trusted_cached_bytes)
customer.refresh()

# After
customer = pickle.loads(trusted_cached_bytes)
customer.reattach_api_key(api_key)
customer.refresh()
customer.save()

customers = pickle.loads(trusted_cached_list_bytes)
customers.reattach_api_key(api_key)
for customer in customers.auto_paging_iter():
    ...

# The same reattachment step applies to pickled events.
event = pickle.loads(trusted_cached_event_bytes)
event.reattach_api_key(api_key)
related_object = event.fetch_related_object()
```

`reattach_api_key()` also attaches credentials to nested unpickled objects. Each retains its saved API version and connected account. Nested objects that already have credentials keep them. Reattachment does not change `stripe.api_key`, and pickling the object again omits the reattached key.

Requests before reattachment raise `AuthenticationError` with instructions to call `reattach_api_key()`, even if a global or per-call API key is supplied. Calling `reattach_api_key()` on a normal object or an already reattached object raises `ValueError`. Empty keys and the serialization placeholder are rejected.

This behavior applies to new pickles produced by this version. Existing pickles may still contain credentials and should be removed or replaced according to your application's storage policy.
