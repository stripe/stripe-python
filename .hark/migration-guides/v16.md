# Migration guide for v16

This version of the SDK uses API version `2026-09-30.endive`. If the format of this API version looks new to you, see our new [API release process](https://stripe.com/blog/introducing-stripes-new-api-release-process).

Please review our API changelog for [`2026-09-30.endive`](https://docs.stripe.com/changelog/2026-09-30.endive) to understand all the breaking changes to the Stripe API, the reasons behind them and potential alternatives.

The Python SDK specific [changelog for v16](https://github.com/stripe/stripe-python/blob/master/CHANGELOG.md#16-0-0) has the corresponding changes in the SDKs as well as SDK specific breaking changes.

## API keys are no longer preserved in pickled StripeObjects

This change applies to v16 releases that include `StripeObject.set_api_key()`. It changes authentication behavior for integrations that persist StripeObjects or webhook events in pickle-backed caches or queues and then make requests through the restored objects. Data-only consumers do not need to rebind credentials.

New pickles omit SDK-held API keys from both the root and nested StripeObjects. Before making object-based requests, explicitly supply credentials from the receiving application's secure configuration:

```python
# Before: relied on the producer's key surviving serialization.
customer = pickle.loads(trusted_cached_bytes)
customer.refresh()

# After: use credentials from the worker's secure configuration.
customer = pickle.loads(trusted_cached_bytes)
customer.set_api_key(worker_api_key)
customer.refresh()
```

`set_api_key()` requires a non-empty string and updates the receiver and every nested StripeObject reachable through payload lists and dictionaries **in place**, including shared objects. It preserves each object's connected-account routing and API version, along with its other requestor options, without changing `stripe.api_key`. The supplied key must be authorized for all accounts represented in that graph. Re-pickling the rebound objects still omits SDK-held keys.

Plain `pickle.loads()` retains the existing fallback to the receiving process's global API-key configuration. A restored object therefore does not necessarily have `api_key is None`. Do not rely on that fallback to select credentials for the intended account; explicitly bind the appropriate worker key before making requests.

### Rolling upgrades and stored data

Upgrade consumers to a release with `set_api_key()` and configure their credentials before updated producers send objects without embedded keys. Do not assume pickle compatibility across SDK versions without verifying your application's producer and consumer versions.

Historical pickles can still contain producer API keys. Upgrading or calling `set_api_key()` does not remove credentials from existing cache or queue entries, replicas, or backups. Identify affected entries and invalidate or recreate them using trusted application sources, handling retained copies according to your operational policy. If credentials reached unauthorized readers, follow your incident-response and credential-rotation procedures. Avoid indiscriminate deletion of production queues.

When object behavior is unnecessary, persist only the required data or identifiers instead. Use recursive data conversion appropriate to your installed SDK version rather than assuming older versions' conversion methods remove every nested StripeObject. This change omits SDK-held authentication context, not secrets explicitly placed in payload fields.

Never deserialize untrusted pickle input: loading it can execute arbitrary code. `set_api_key()` does not make deserialization safe.

## Rename `stripe.Reversal` to `stripe.TransferReversal`

The class representing a transfer reversal has been renamed from `stripe.Reversal` to `stripe.TransferReversal`.

This change affects integrations that reference `stripe.Reversal` directly, including imports, class comparisons, `isinstance` checks, and type annotations. Replace those references with `stripe.TransferReversal`:

```python
# Before
reversal = stripe.Transfer.retrieve_reversal("tr_123", "trr_123")
isinstance(reversal, stripe.Reversal)

# After
reversal = stripe.Transfer.retrieve_reversal("tr_123", "trr_123")
isinstance(reversal, stripe.TransferReversal)
```

The methods for creating, retrieving, modifying, and listing transfer reversals have not changed. Code that only calls those methods and reads attributes from the returned object does not require an update.

## `StripeObject.request()` has been removed

The deprecated `StripeObject.request()` method has been removed. If you used it to make custom API requests, create a `StripeClient` and use `raw_request()` instead:

```python
# Before
response = stripe_object.request("get", "/v1/example")

# After
client = stripe.StripeClient("sk_test_...")
response = client.raw_request("get", "/v1/example")
```

## Path parameters must now be passed positionally

Path parameters must now be passed positionally instead of by keyword.

For example, a customer ID that was previously accepted as a keyword argument:

```python
customer = client.v1.customers.retrieve(customer="cus_123")
```

must now be passed positionally:

```python
customer = client.v1.customers.retrieve("cus_123")
```

This also affects legacy resource methods that support both classmethod and instance-method call styles. For example, `Customer.retrieve_payment_method`:

```python
# Before
payment_method = customer.retrieve_payment_method(
    payment_method="pm_123"
)
payment_method = stripe.Customer.retrieve_payment_method(
    customer="cus_123", payment_method="pm_123"
)

# After
payment_method = customer.retrieve_payment_method("pm_123")
payment_method = stripe.Customer.retrieve_payment_method(
    "cus_123", "pm_123"
)
```

Update calls to your methods to pass path parameters before any request parameters or options.
